# Success Metrics

What each metric from the original punch list means, exactly how `GET /api/admin/success-metrics` (admin-only) computes it, and where it's a direct measurement versus a labeled proxy. No separate analytics pipeline exists or was added for this - every number here comes from data this app already persists for other reasons (simulations, decisions, incidents, the new opt-in chat ratings), consistent with `docs/PRIVACY.md`'s "no analytics integration" stance.

| Metric | Definition | How it's computed | Caveats |
|---|---|---|---|
| **Time to first simulation** | How long after signing up a real account took to run its first "own data" simulation | Median of (first `RiskSimulation.timestamp` for that `owner_email` − that `User.created_at`), across accounts that have run at least one | Only covers real registered accounts (`models.User`) - the two demo identities (`ciso`/`cfo`) have no `created_at` to measure from and are excluded, which is correct: this metric is about the real-signup funnel |
| **Percentage of users completing onboarding** | Share of registered accounts that ever ran an own-data simulation | `accounts with >=1 own-data simulation / total registered accounts` | A proxy - "ran a simulation" is used as the definition of "completed onboarding" since there's no separate onboarding-completion event tracked anywhere in the app. Reasonable given the app's actual flow (sign up -> pick Own Data -> ingest or seed data -> run a simulation), but would need a real definition if onboarding is ever redesigned |
| **Recommended controls accepted** | How often the optimizer's top-ranked recommendation actually got funded in the resulting decision | `decisions where recommended_control_not_funded IS NULL / total decisions` | `recommended_control_not_funded` (see `models.RiskDecision`) is set server-side at decision time from the optimizer's actual output, so this is a real measurement, not a survey - but it can't distinguish "recommendation was funded" from "no recommendation existed to fund" (an edge case for very early runs with no optimizer output yet) |
| **Number of calibrated incidents** | How much real ground-truth the Closed-Loop Calibration Engine has to work with | `COUNT(IncidentRecord)` | Direct count, no caveats |
| **Prediction error over time** | Whether FAIR predictions are getting more or less accurate as real incidents accumulate | Full `(incident_date, prediction_error_pct)` series, plus mean absolute error for the most recent 10 incidents vs. everything before that | `prediction_error_pct` is computed once per incident at logging time (see `IncidentRecord`'s docstring) and never recalculated later, so this reflects prediction accuracy *as of when each incident was logged*, not a live recomputation |
| **Audit decisions with complete evidence** | Whether board-approved decisions actually carry the evidence a board would need | `board-approved decisions with residual_ale/p95/accepted_scenario/evidence_hash all present / total board-approved decisions` | Should always read 100% today - `POST /api/audit` has hard-rejected an incomplete board-approval since the governance-evidence fix (item #59), so this field is really a **regression detector**: a drop below 100% would mean either a legacy pre-fix row or that validation broke, not that the app is behaving as designed |
| **AI answer usefulness** | Whether people find the Virtual CISO's answers helpful | `thumbs-up ratings / total ratings`, from the new opt-in per-message rating buttons in `VirtualCisoChat.tsx` | Entirely new instrumentation added for this metric (`POST /api/chat/feedback`, `models.ChatFeedback`) - only counts messages a visitor explicitly rated, so it reflects the engaged subset of users who bother to click, not every conversation. Excludes `[Offline Mode]` fallback answers (rating a canned response for "AI usefulness" isn't meaningful) |
| **API and simulation failure rates** | Operational health, not product usefulness, but tracked here since it was on the original list | Reuses `backend/observability.py`'s existing in-process counters (`get_summary()`) - request 4xx/5xx rates and simulation success/failure counts | Resets on every process restart (see `observability.py`'s module docstring) - this is a live, since-last-restart snapshot, not a historical trend. For a long-lived trend, these would need to be exported to a real time-series store, which this app deliberately doesn't run (see observability.py's dependency-free rationale) |

## Using it

`GET /api/admin/success-metrics` (requires an admin/demo account - see `backend/security.py::require_admin`) returns all of the above as one JSON document, grouped by category (`onboarding`, `recommended_controls`, `calibration`, `audit_evidence`, `ai_answer_usefulness`, `api_and_simulation_failure_rates`). There's no dashboard UI for it yet - pull it from Swagger (`/docs`) or `curl` it with an admin bearer token.

## What this deliberately doesn't do

No client-side event tracking, no third-party analytics SDK, no cookies beyond what auth already uses. Every metric above is derived from data the app needed to persist anyway for its actual features (simulations, decisions, calibration, and now opt-in chat ratings) - see `docs/PRIVACY.md` for the full data-handling policy this stays consistent with.
